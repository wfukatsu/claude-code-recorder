# prompt-coach

ccrec の記録から、**人間が AI に出す指示**の改善点を見つけて、根拠と理由つきで伝える。
AI の振る舞い（無駄なツール呼び出し、迷い、モデルの選び方）は、それ自体を責めるためではなく、
**どんな指示ならそれを防げたか**を考える手がかりとして使う。

## 守ること

- 読み取りだけ。ccrec は `sessions` / `summary` / `show` / `export` / `usage` だけを使う。
  `delete` / `ingest` / `import` は呼ばない。
- 記録にはプロンプト、ソースコード、伏せ字にならなかった秘密情報が入りうる。分析結果とレポートは
  ローカルのファイルにだけ書く。外部のサービスへは送らない（Artifact にも公開しない）。
- 対象は、頼んだ本人のアカウント（`ccrec whoami`）の記録だけ。別のアカウントを頼まれたら、
  本人の同意があるかを確かめる。
- 指摘には必ず根拠（セッション、時刻、引用）を付ける。根拠のない一般論は書かない。
- 引用は 1 か所あたり 2〜3 文に留める。

## 手順

### 1. 範囲を決める

- 既定は直近 7 日。「今日」「先週」「このセッション」などの指定があれば合わせる。
- セッション ID が分かっていれば `--session <id>`（複数可）。
- 直近 1 件だけを見たいと言われたら、`ccrec sessions --limit 1` で ID を取ってから `--session` で渡す。

### 2. 数える

このスキルのベースディレクトリにある `scripts/analyze.mjs` を実行する。Node 18 以上と ccrec が要る
（Java は自分で探す）。結果はプロンプトを含むので、作業用の一時ディレクトリに書く。

```bash
node <skill-dir>/scripts/analyze.mjs --days 7 --out <tmp>/prompt-coach.json
node <skill-dir>/scripts/analyze.mjs --session <id> --out <tmp>/prompt-coach.json
```

30 セッションで 1 分ほどかかる。失敗したら、標準エラーの 1 行目を見て直す
（多いのは Java が見つからない、ccrec が無い）。`scope.skipped` に入ったセッションは、
レポートに読めなかったと書く。`scope.truncated` が true なら、期間内のセッションの一部が
漏れている可能性がある。`--limit` を大きくして実行し直す。

期間を指定したときは、その期間に起きたことだけを数える。前から続いているセッションでも、
期間より前のプロンプトやツール呼び出しは入らない。

出力の形:

- `scope`: 期間、セッション数、モデル別のトークン（`tokensByModel`）、
  作業を頼んだプロンプト（承認や相づちを除く）のうち完了条件・制約・対象（パス、URL、コード、
  貼り付け）を含む数（`promptProfile`）。どのプロンプトもフラグにならなくても、ここに癖が出る
- `patterns`: フラグの種類ごとに、出たセッション数と回数。**複数セッションで出るものが癖**
- `sessions[]`: `metrics`（トークン、キャッシュ率、思考の比率、最大コンテキスト、圧縮、ツール）、
  `prompts`（人が打ったプロンプトと、含む要素、その後のツール呼び出し数）、
  `flags`（種類、観点、深刻度、詳細、根拠の抜粋）

### 3. 判断する

`references/rubric.md` を読んでから判断する。フラグは**読むべき候補**であって、結論ではない。

1. `patterns` を上から見て、2 セッション以上で出ている種類を優先する。
2. 各フラグの `evidence` を読み、rubric の「問題でない場合」に当たらないかを確かめる。
   当たるものは捨てる。
3. 抜粋だけでは判断できないときに限り、前後を読み足す。
   - `ccrec export <id> --no-tools --out -`（プロンプトと応答だけの Markdown）
   - `ccrec show <id> --full --kind tool_use,tool_result`（ツールの入出力）

   出力が大きいときは、`grep` で時刻やキーワードの近くに絞って読む。
4. `scope.promptProfile` と `prompts` の `features` も見る。完了条件（`criteria`）、制約
   （`constraint`）、対象（`path` / `url` / `code` / `pasted`）が一貫して欠けているなら、
   それ自体が指摘になる。`pasted` は貼り付けがあったことだけを示し、中身は分析結果に入れていない。
   中身が判断に要るときだけ `ccrec show` で読み、レポートには引用しない（秘密情報が入りやすい）。
5. AI 側の問題（迷い、重複、モデル）は、**指示の何を変えれば防げたか**まで掘り下げる。
   指示と関係のない AI 側だけの問題（ツールの不具合、API エラー）は、
   短く「参考」として触れるだけにする。

### 4. 書く

`references/report-template.md` の構成で、作業ディレクトリに `prompt-review-<YYYY-MM-DD>.md` を書く
（同名があれば `-2` を付ける）。各指摘には次の 4 つを必ず付ける。

1. **何が起きたか**: セッションのタイトル、時刻、引用
2. **指示のどこが原因か**
3. **こう書くとよい**: その場面に合わせた書き換え例。一般的なテンプレートは書かない
4. **なぜよいか**: AI の動き方に即した理由（rubric の説明を、その場面に当てはめて書く）

指摘は 5〜8 件までに絞り、効果の大きい順に並べる。よかった点も 1〜3 件、根拠つきで書く。

分析結果の時刻は UTC（ISO 8601）なので、レポートでは利用者の地域の時刻に直して書く。

書き終えたら、送る前に次を確かめる。引用を別のセッションに付けてしまう誤りが起きやすい。

- 引用した文言を、分析結果の JSON で文字列検索する。見つかったセッションのタイトルと時刻が、
  レポートに書いたものと一致するか
- 「何が起きたか」に書いた AI の動き（ツール呼び出しの数、撤回、見つかった問題）は、
  数字なら分析結果に、それ以外なら読み足した記録にあるか。確かめていないことは書かない
- 表の数字（合計、件数）を分析結果から計算し直したか

### 5. 伝える

会話には、レポートのパスと、上位 3 件の要点（1 件 1〜2 文）だけを書く。数字は、トークンの合計、
キャッシュ率、圧縮の回数など、判断に効いたものだけを出す。
